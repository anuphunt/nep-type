# Lekha: phased product plan

**Status:** The standalone Mac pad and experimental input adapters have progressed across several phases, but product-quality and native-host acceptance remain incomplete. The user authorized continuing across phases and will handle Aksharantar commercial licensing before distribution. IndicXlit and online decision services remain deferred. Estimates, acceptance thresholds, purchases, installation, external processing, signing, and release remain subject to the decisions and permissions described below. See `LEKHA_READINESS.md` for current platform status; dated entries below are historical.

## Goal and product principles

Build a distributable macOS input method for people who naturally mix Romanized Nepali and English. It should produce useful Nepali suggestions while preserving English words and phrases, and let the user correct its choices easily. A representative target is:

> `aaja mero phone ko battery literally dead bhaisakeko thiyo`  
> → `आज मेरो phone को battery literally dead भइसकेको थियो`

Do not assume a Roman word has only one interpretation: `man` may mean English “man” or Nepali “मन”; English loanwords such as `football` can be written either `football` or `फुटबल`. Show alternatives, preserve access to the original, and allow explicit English/Nepali control. Protect URLs, email addresses, code and other literal text. Processing should be local by default. Typing must remain responsive when a model, lookup, or network service is slow or unavailable.

**Current state:** The standalone Swift/AppKit pad uses local curated entries, English and Nepali indexes, context heuristics and a phonetic fallback. It runs offline and offers live preview, choices and access to the original text; its mixed-language decisions are heuristic and can be wrong. The separate InputMethodKit bundle compiles, but has **not** been installed, activated, or verified in other apps. Other platforms have experimental adapters with differing capabilities and test coverage. Do not install an input source or change system settings without the required approval.

## Phase 0 — Baseline and evaluation set

- **Scope:** Document current behavior and limitations; agree on representative intended use. Build a versioned, reviewable evaluation set with mixed-language sentences, English spans, long and short words, ambiguous cases, spelling variants, borrowed words, names, Unicode, punctuation, URLs, email, code, and the example above. Include alternative acceptable outputs and original-preserving choices where intent is ambiguous. Record sources and permission for every example; use synthetic or explicitly consented material, not private keystrokes collected by default. Reserve a held-out set that is not used to tune rules.
- **Dependencies:** Current standalone pad and engine; user input on representative spelling and acceptable behavior.
- **Acceptance tests:** Reproduce and record the current result for each example; verify the evaluation runner separates English preservation, Nepali word accuracy and suggestion availability. Measure a baseline on a specified Mac and dataset. The full example and `football`/`फुटबल` alternatives are present.
- **Decisions:** Agree on dataset ownership, annotation process, language/script convention and whether per-word or sentence-level accuracy matters most. Set numeric targets only after seeing baseline results.
- **Risks:** Small or biased examples exaggerate quality; one reference spelling can penalize valid alternatives. Avoid capturing real sensitive text without informed permission.

### Phase 0 outcome (baseline recorded; review pending)

The initial versioned evaluation and runner are in `evaluation/phase0/`. On the 10-case frozen comparison split, the current engine achieved **7/15 English words preserved**, **22/28 Nepali words correct at top 1**, and **2/10 exact sentences**; an acceptable candidate appeared for 15/15 English and 22/28 Nepali tokens. Development split and per-case output are in `evaluation/phase0/README.md` and `baseline-results.json`. These are small, synthetic, provisional examples, not product accuracy claims; the comparison split is readable and has been measured, so it is not a blind independent test. The user’s target sentence is not currently rendered correctly.

Remaining before considering this phase fully accepted: review Nepali spelling/intent annotations and alternatives, agree on data ownership and future consent process, define token versus sentence priorities, and set numeric goals. At the time of this baseline, no later phase had been started; later work is documented below. The input source remains uninstalled and unverified.

## Phase 1 — Local candidate indexes and data provenance

- **Scope:** Design efficient offline English and Nepali candidate indexes. Nepali entries should map common Roman spellings to one or more Devanagari forms, including frequencies where legitimately available; English entries should support case and inflections without blindly preserving every ambiguous word. Retain the original Roman text as a candidate and keep a deterministic fallback for unknown words. Define an updateable data format and reproducible index build.
- **Dependencies:** Phase 0 baseline and data criteria. Before incorporating any source, record its origin, version, copyright, license, commercial redistribution and attribution terms, modifications, and whether derived indexes can be shipped. Separately review dataset, code and model licenses; treat uncertain terms as a blocker for that source. The existing handwritten data remains available.
- **Acceptance tests:** Exact candidate lookup and alternate spellings work offline; `football` offers both forms; held-out regression cases cover English words and Nepali variants; literals remain unchanged. Verify index reproducibility, size, startup time and lookup latency on the agreed Mac. Produce a provenance inventory and check that no unapproved dataset is bundled.
- **Decisions:** Choose data sources only after license review; decide normalization, inflection handling, storage limits, how updates are delivered, and whether a user dictionary is included. No paid dataset or license is approved by this plan.
- **Risks:** English and Romanized Nepali overlap; word-list licensing or redistribution can prevent shipment; frequency lists may encode regional bias or miss names and newer vocabulary.

### Phase 1 outcome (implemented; quality and commercial review pending)

The normal local build includes reproducible offline English membership, curated Nepali, Google pronunciation-derived suggestions and an Aksharantar index of 2,171,523 IndicCorp-labeled training keys. At Phase 1, Aksharantar suggestions were marked † and required selection; Phase 2 can now choose a unique entry when local evidence supports it. The original text remains available. The user requested normal-build integration and will handle commercial licensing before distribution. Source rights and commercial redistribution remain unresolved; do not treat integration as clearance. Full provenance and attribution accompany the index.

Thirteen Swift tests and 21 UI checks passed. A 59-word provisional probe had 45 intended words in the visible suggestions, versus 44 before; the separate 4,101-row Aksharantar test split had zero exact Roman-key overlap with the training index, exposing a generalization limitation. `evaluation/phase1/REPORT.md` records exact metrics, performance, reproducibility and limitations. Independent speaker-reviewed evaluation and agreed quality targets remain open. At the time of this Phase 1 outcome, Phase 2 contextual ranking had not yet been implemented; its later prototype is described below. The input source remains uninstalled.

## Phase 2 — Context-aware bilingual ranking

- **Scope:** Score candidate spans using local English and Nepali indexes, word and phrase context, frequency, spelling variants and prior explicit choices if the user enables them. Preserve coherent English spans such as `phone`, `battery literally dead`; rank Nepali forms for surrounding words. Keep manual language selection and an original-text candidate. Define a confidence/abstention policy for ambiguous text and present alternatives rather than silently forcing a low-confidence choice. Keep automatic behavior reversible; the user remains in control.
- **Dependencies:** Phases 0–1; chosen local index data and a clear definition of confidence. Start in the standalone pad so the ranking can be evaluated without system installation.
- **Acceptance tests:** The goal sentence renders as specified and offers original/alternate candidates; changing one word does not corrupt surrounding text. Test `man`, `pani`, `football`, names, all-English sentences, all-Nepali sentences, punctuation and protected literals. Compare held-out English-preservation errors, Nepali accuracy and candidate recall against Phase 0; agree on improvement thresholds before acceptance. Measure input-to-visible-response latency, including p50/p95/p99 on an agreed device and longer text; no perceptible blocking or data loss.
- **Decisions:** Select ranking features, confidence thresholds, UI for uncertain words, and any local learning/retention rules. User corrections must not be sent elsewhere by default.
- **Risks:** Context can still guess wrongly; false conversion of English may be more disruptive than leaving a Nepali word Romanized. Heuristics and any learned preferences require bias and regression checks.

### Phase 2 outcome (prototype implemented; quality acceptance pending)

The standalone pad now uses local heuristic evidence from curated words, English and Nepali indexes and immediate neighbors. It surfaces an uncertainty prompt and allows alternatives, original text and undo. No cloud, learned user data or system input installation was added. On the earlier 10-case comparison split, English preservation improved from 7/15 (Phase 1) and 13/15 (dataset-first) to 15/15, while Nepali top-1 stayed 22/28. A new 20-sentence synthetic check yielded 17/20 exact, compared with 9/20 and 14/20 for those prior engines; it was not blinded or speaker reviewed. On the separate 4,101-word Aksharantar test, top-1 exact declined from 430 to 367, including names that were incorrectly retained as English. `evaluation/phase2/README.md` records methodology, shortcomings, app tests and performance. The user’s target sentence still needs a candidate correction for `भइसकेको`. Phase 2 quality acceptance requires broader independent bilingual review and agreed targets. Later experimental platform work is documented below.

## Phase 3 — Optional local transliteration benchmark

- **Scope:** If approved, benchmark IndicXlit alongside the existing local engine on the same held-out examples. Check candidate quality, Nepali support in the exact model, load time, memory, app size, CPU/battery use, installation and offline behavior on supported Macs. Investigate runtime, model, training-data and dependency licenses and whether each can be redistributed commercially. IndicXlit is a candidate for comparison, **not an assumed dependency or integration**.
- **Dependencies:** Phase 0 evaluation; Phase 1 provenance process; a representative build environment. No model or dataset should be shipped before license and distribution review.
- **Acceptance tests:** Produce a reproducible comparison of top-1 accuracy, top-k candidate recall, English false conversions, p50/p95 latency, memory and package size against the local baseline. Verify operation without network access, and record license/redistribution findings and unresolved questions.
- **Decisions:** Integrate, use as an optional component, defer, or reject based on evidence and agreed product constraints. Any download, third-party data license or extra distribution obligation requires separate approval where applicable.
- **Risks:** Model quality may not transfer to colloquial mixed text; a usable model may be too large, slow, or legally unsuitable for a distributed app.

## Phase 4 — System-wide macOS input method

- **Scope:** Integrate the accepted local engine into the existing InputMethodKit work. Support marked composition, candidate display and selection, commit/cancel, backspace, cursor movement, English/Nepali switching, per-session state, undo and robust Unicode handling across apps. Keep the standalone pad as an engine test and preview tool. Define safe behavior for secure fields and sensitive input, using system-provided signals and conservative fallbacks.
- **Dependencies:** Phases 1–2 sufficient for a useful engine. **Installation and activation require the required user approval**; a compiled bundle alone is not proof it works. Plan the exact install, registration, removal and rollback steps before asking for that approval. Do not require broad event monitoring or accessibility permissions without a demonstrated need and separate review.
- **Acceptance tests:** After approved installation, verify input-source registration, switching, typing and candidate selection in agreed native and browser apps; test composition, punctuation, long text, edit/undo, multi-code-point Devanagari and emoji, focus changes, app quit/relaunch, and removal. Confirm original text is recoverable and ordinary shortcuts remain usable. Test supported macOS versions and document app-specific failures.
- **Decisions:** Agree on input menu, shortcuts, candidate UI, supported apps/macOS versions, secure-field behavior, installation method and uninstall experience.
- **Risks:** Host applications differ in composition support; secure fields may bypass input methods; system registration can require session restart. Treat unverified hosts and restrictions as gaps, not as passed tests.

### Phase 4 work in progress (host testing pending)

The experimental input source now uses the shared offline context engine with per-client marked composition, candidate window callbacks, original-text cancellation, candidate cycling, host shortcut handoff and bounded in-memory prior-word context. Twenty core tests passed and the IMK server started; these do not verify actual host applications or registration. `docs/PHASE4_INPUT_METHOD.md` records install/removal, controls and known limitations, including that word-at-a-time composition can corrupt URLs or code and secure-field behavior is unverified. Host-app behavior, input-source registration, undo and compatibility remain unverified; Phase 4 is not accepted.

## Phase 5 — Optional opt-in Jev/OpenAI fallback

- **Scope:** Only if explicitly approved after the local path is useful, investigate Jev/OpenAI as an optional fallback for uncertain cases. Define exactly which short text span and context would be sent, the consent and settings UI, and user-visible indicators. Use local results immediately and treat remote results as suggestions. Never block a keystroke, silently rewrite committed text, or apply a result after the user has changed the composition, moved focus, or switched sessions. Bind requests to a composition/session ID, generation and exact source snapshot; discard stale, timed-out and failed results. Permit cancellation; offline mode remains functional.
- **Dependencies:** Phases 0–2, opt-in UX and threat review; coordinate with Phase 4 composition semantics if used system-wide. Evaluate actual provider capabilities and terms before selecting one. No provider, paid account, model, or budget is approved here.
- **Acceptance tests:** With mocked slow, failed, reordered and duplicate responses, typing and local candidates stay responsive, and stale results never change text. Verify no requests with opt-in off or for protected/secure contexts; confirm the user can disable the feature and see what is transmitted. Compare marginal quality gains, p50/p95 network latency and cost per request and per representative user/month, including rate limits and failures. Test timeouts, cancellation, abuse prevention and offline fallback.
- **Decisions:** Decide whether benefits justify privacy, latency and operating costs; choose provider/model and data retention only after reviewing current terms. Decide explicit opt-in, consent wording, configurable context, quotas and budget ceilings before implementation or deployment.
- **Privacy and key security:** Do not embed provider API keys in the distributed app. If a backend is chosen, keep provider credentials server-side, use appropriately scoped user/session authorization, rate limits, spending caps, secret rotation and abuse monitoring. Minimize transmitted text; define retention, deletion and logging policies, and avoid logging sensitive text by default. Document third-party data handling accurately; never claim zero retention without verification.
- **Risks:** Even opt-in text may contain sensitive information; network delays and service changes affect reliability; a backend introduces ongoing security, moderation and cost responsibilities.

## Phase 6 — Product QA and readiness

- **Scope:** Run a structured evaluation of the entire local flow and, only if enabled, the optional remote flow. Expand consented participant testing across Nepali dialects, spelling styles, bilingual contexts, new users and accessibility needs. Test supported macOS versions, hardware, large documents, app compatibility, install/uninstall, updates, offline operation, performance, battery/memory, crash recovery, privacy and security.
- **Dependencies:** Completed phases selected for the first release, plus approved test environments and participants. System tests depend on approved installation; remote tests depend on separate service approval.
- **Acceptance tests:** Publish a test matrix and reproducible results against agreed targets, including held-out English preservation, Nepali accuracy, top-k recall, correction rate, p50/p95/p99 latency and crash/data-loss rates. For an enabled service, include request rate, cost estimates and stale-response tests. All release-blocking defects are fixed or explicitly accepted; known limitations are documented.
- **Decisions:** Agree on target thresholds, supported macOS/app matrix, accessibility standard, beta audience, issue severity and release go/no-go criteria.
- **Risks:** Synthetic tests may miss real typing habits; rare corruption or privacy issues can be high impact despite good aggregate scores.

## Phase 7 — Distribution and release

- **Scope:** Prepare a distributable Mac product: reviewed branding, onboarding, input-source install/activation and removal, signed and notarized build or other approved channel, update and rollback strategy, privacy notice, support and clear documentation. Review licenses and attribution for all code, data and models. Evaluate an appropriate distribution channel and any account requirements at that time.
- **Dependencies:** Phase 4, Phase 6 and a release decision. Signing accounts, hosted infrastructure, publication and any external release require their own authorization. An ad-hoc signed local prototype is not a release build.
- **Acceptance tests:** On a clean supported Mac, install, activate, type, switch languages, update, roll back and uninstall using the documented path; verify signed artifacts and integrity. Confirm offline local use, privacy settings, third-party license notices, support contact and release notes. Any optional online service must pass Phase 5 and have an approved cost and operational plan.
- **Decisions:** Choose release channel, pricing if any, supported versions, update cadence, privacy policy and operational ownership. Conduct a final review before distribution.
- **Risks:** macOS signing, notarization, sandbox and input-source policies can affect packaging; support and infrastructure costs can exceed development estimates; released datasets and dependencies may carry obligations.

## ViKey parity roadmap — research snapshot, 30 October 2026

**Direction:** Make Lekha a polished, cross-platform Nepali–English keyboard with functionality comparable to ViKey, adapted for Nepali romanization. The milestones below extend the existing phases and do not change their recorded completion status. ViKey is a Vietnamese Telex product, so literal replication of Vietnamese tone rules is not a Nepali requirement. Treat parity as a moving target: review the current product and release notes at each milestone.

**Evidence and limits:** The [official ViKey home page](https://vikey.app/en/), [downloads](https://vikey.app/en/download), and [FAQ](https://vikey.app/en/faq) were read in a browser on 30 October 2026. The site claims 99.73% mixed-language word accuracy on its stated evaluation of almost two million words; that number is not independently verified and is not a transferable Nepali benchmark or acceptance threshold. No ViKey software was installed or its typing behavior tested. Its [repository](https://github.com/tonyminibot/Vikey) is GPL-3.0; independently implement Lekha and do not copy its code or proprietary artwork without an explicit licensing decision.

### Preserve corrections across earlier edits
