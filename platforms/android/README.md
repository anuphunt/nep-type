# Lekha Android — offline candidate experiment

The project includes an original native setup activity with user-triggered links to Android's keyboard settings and picker, plus a 2–4 candidate display preference. It does not enable or select Lekha itself. The original word remains shown separately, and the display preference is read at the next input session. The activity, preference integration, Android settings navigation, accessibility and field safety have **not** been compiled or exercised on Android. The existing JDK test verifies preference bounds and the XML parses; these do not validate the native UI.

This is an **uncompiled, uninstalled experimental keyboard**, not production-ready. It is not the same ranking engine as macOS. The Java service keeps Roman text as marked composition and looks up exact Roman spellings in the project-authored Nepali lexicon, Aksharantar and Google-derived indexes on a background worker. Tapping a suggestion selects a reversible preview while the Roman token remains marked. Tap “Use” to replace it, or cancel the choice and keep the original; pressing space commits the original. English mode sends literal keys. If indexes are unavailable, the original remains the default. Stale worker results are discarded after subsequent typing, switching or focus changes. The implementation does not automatically determine English versus Nepali or match the Mac's context ranking, and index candidates can be noisy. Literal mode remains safest for code and sensitive text.

The app contains no network permission. It packages the same 94 MB Aksharantar and 10 MB Google alias indexes used by the Mac prototype, in uncompressed APK assets so it can seek them without loading either into memory. The original dataset's attribution and manifest are included in `app/src/main/assets`; the user will handle Aksharantar commercial licensing before distribution, which remains unresolved. Resource size, load/lookup latency, memory and Android packaging have not been measured on a device. Do not ship before license review.

## Verification on the development Mac

A usable existing JDK is at `/opt/homebrew/opt/openjdk/bin` (Java 27). With `JDK_BIN` set to an installed JDK's `bin` directory, run:

```sh
JDK_BIN=/opt/homebrew/opt/openjdk/bin ./tests/run-core.sh
```

This compiles and runs the platform-independent Java index/composition tests: 600 deterministic synthetic indexed keys, byte segment boundaries, duplicate candidates, original-text preservation and English mode, plus representative lookup checks against the bundled actual indexes. An independent spot check of ten actual indexes on the Mac observed approximately 0.6–6.7 ms per lookup; this is not an Android benchmark or an accuracy estimate. The Android manifest and input-method XML parse successfully.

No Android SDK, Gradle or adb was found in the checked environment. Consequently neither the service source nor the Android package has been compiled, installed, activated or exercised. The Gradle project requests AGP 8.9.3 and SDK 35, whose compatibility has not been verified. Do not install or enable the prototype without required user authorization.

## Open safety and product work

- A rejected `setComposingText` invalidates local state and is not retried because the host may have applied it despite returning false. The new keystroke may be missing, and the old marked span may remain in the host; this uncertainty must be resolved with real-host tests before use. Missing composing ranges with a selection change invalidate local ownership and stale candidates.
- Test InputConnection marked-text replacement, user-selected candidates, stale callback rejection, focus changes, cursor movement, deletion, editor action, hardware keys and host failures on actual Android apps and devices. Android APIs may report selection or composing ranges differently across clients; the current checks cannot guarantee against stale edits. Secure fields and IME lifecycle are unverified.
- Expand and test numeric/symbol layouts, punctuation, host-specific enter actions, accessible touch targets, visual resizing and accessibility. The current UI rebuilds views per key and its performance is unknown.
- Use shared versioned engine/conformance fixtures and make a deliberate ranking/portable-core decision; the three local index layers use simple exact match and preserve source order. Do not claim model accuracy or equivalence to the Swift engine.
- Verify SDK/Gradle dependencies, reproducible source and asset hashes, build Android with an approved toolchain, and run the real-device and privacy matrix before any distribution.

## Additional input safety and return-action work

The service now invalidates local composition and pending suggestions after a failed candidate replacement, failed composition deletion, or failed finish operation; it never automatically retries an uncertain host edit. Such failures may still leave the host's actual text or cursor in an unknown state. Pure-Java tests cover current/stale candidate generations, changed text, cursor moves, selections, missing/malformed composing ranges and host return-action decision flags. The return key attempts an explicitly requested editor action (such as Done or Search) unless the host requests a newline; otherwise it inserts a newline. Actual Android editor interactions, callback ordering and API compilation remain unverified because the Android SDK is unavailable. Failed or asynchronous editor actions are not retried. These tests do not prove host text integrity.

## Project-authored candidate index

The entire project-authored `data/sources/nepali-authored-v1.json` lexicon (259 Roman keys) is transformed reproducibly to the byte-sorted `app/src/main/assets/nepali-authored-v1.tsv` by `python3 scripts/build-authored-index.py`; use `--check` to detect drift, or `--source /path/to/nepali-authored-v1.json` for a separate workspace. Candidate lookup merges sources in priority order: authored alternatives first, followed by Aksharantar, then Google aliases, preserving each source's order, removing duplicates and limiting the visible list to four. The Roman original remains marked while a candidate is previewed; only the explicit Use action replaces it, and space retains the original. This adds authored candidates, not the Mac engine's phonetic fallback, contextual scoring, automatic classification or exact overall candidate ranking. Tests check authored `football` and `bhetau`, source-order merging, original preservation and generator reproducibility. The authored data is project-authored; dataset attribution and commercial licensing status remain as previously documented. `ASSET_HASHES.sha256` covers the generated index. Android host code remains uncompiled and untested on-device.

## Literal-field safeguards and basic symbols

A pure Java classifier treats numeric/unknown fields, Android password variants, URI/email address fields, and the `TYPE_TEXT_FLAG_NO_SUGGESTIONS` flag as literal-only. In those fields the service avoids constructing Roman composition and candidate requests; it passes typed text to the host. Classification is based on the input type supplied by the host; misclassified or changing fields are not guaranteed protected. Normal text fields remain explicit-choice only. A 128-character composition bound prevents unbounded in-memory tokens; at the boundary the service finishes the existing original and passes the next character through. A basic `?123` page adds numbers and common punctuation, with a return to letters. Java tests cover field classification (including unknown variants), length bounds and mixed English/Nepali explicit choices; `tests/run-core.sh` and asset/provenance checks passed. The pure Java core tests compile with `javac --release 8`; this does not compile the Android service. Reference: [Android InputType](https://developer.android.com/reference/android/text/InputType).

The service and symbol page are **not compiled or tested in Android**, since SDK/Gradle/adb were not found in checked locations. Host declarations may be absent or inaccurate, `InputConnection` failures may still have uncertain results, sensitive-field lifecycle is unverified, and actual performance, touch layout, accessibility and host-specific return actions need device testing. Do not rely on this as a security guarantee.

## Candidate and selection safety update

The candidate row includes an explicitly labeled “keep original” control. Candidate buttons capture the exact token and generation they represented; delayed clicks are ignored if either has changed. Shift and language controls announce their current state through accessibility labels. These are source-level improvements; TalkBack, key sizes, narrow-screen layout and focus behavior have not been tested on Android. The keyboard still rebuilds its views during editing, which may disrupt accessibility focus.

Selection ownership is now relinquished if the host reports an unknown, malformed or differently sized composing range, or a selection outside the expected end. The keyboard does not finish or replace a marked span once ownership is uncertain. Some Android editors may omit composing ranges or send delayed callbacks even during normal composition; this conservative policy may cancel suggestions prematurely and leave marked text under the host's control. A rejected or ambiguous host edit can still lead to missing input, and real `InputConnection` behavior needs device testing. Pure Java tests cover the decision logic and candidate-generation guard; they do not execute Android APIs.

## Reversible candidate preview

A suggestion tap now selects a preview without changing the host’s marked Roman text. Another suggestion can replace the preview, “Cancel choice” discards it, and “Keep original” or space commits the original. The separate “Use” action is the only replacement operation and validates the displayed token, generation and candidate list again. This makes a mistaken choice reversible before commit; it is not post-commit undo. Once a replacement is committed, host undo is not implemented because there is no verified safe ownership of the committed range. A failed or ambiguous replacement still relinquishes local state without retry; host text can remain uncertain. Pure Java tests cover preview switching, stale results and cancellation. The Android service and accessibility controls remain uncompiled and untested on-device.

## Manual language memory and post-commit undo

For ordinary text fields, a manual language toggle is remembered per `EditorInfo.packageName` while this keyboard process is running, with an in-memory least-recently-used limit of 64 app names. A newly encountered or unknown app defaults to Nepali; by default app choices reset when the process ends. The separately described opt-in setting can persist later explicit choices. Literal-only fields neither change the stored preference nor allow the language toggle. No surrounding text is used for preferences. The service integration is uncompiled and actual Android lifecycle, field identity and focus behavior require device testing.

Post-commit undo is intentionally **not exposed in the Android service**. The dormant `VerifiedUndo` contract and Java tests require a host's single atomic compare-and-replace over the exact committed text, caret and session, reject stale/unavailable/ambiguous outcomes and never retry. Android's public InputConnection does not supply such an atomic conditional replacement; even verifying surrounding text and caret before separate selection/replacement operations leaves a race with another host edit. The [Android InputConnection documentation](https://developer.android.com/reference/android/view/inputmethod/InputConnection) states that `takeSnapshot` is unavailable to IMEs, and its selection/commit methods are separate operations. A no-op guarded model is not a functioning undo. Do not wire it into the keyboard until an actually safe host-specific mechanism and real-device tests demonstrate ownership and failure behavior; candidate previews remain reversible before commit.

## Experimental failure feedback

The service now shows an accessible, dismissible notice when an app does not confirm an edit. It does not retry the uncertain edit; the notice asks the user to check their text and remains visible through later successful edits until dismissed or a new input session begins. If all three candidate indexes fail to open, a separate notice explains that suggestions are unavailable. No notice contains the user's typed text or application identity. Candidate button labels are shortened visually when necessary while their accessibility descriptions retain the full label. These UI integrations are source-level only: pure Java tests cover the notice state and priority, but the Android service has not been compiled, run on Android or tested with TalkBack. A notice cannot guarantee that the host preserved a failed edit.

## Ownership-loss review

A marked range can remain in an editor after the IME loses confidence in ownership. Previously the service cleared its local state but could immediately call `setComposingText` or `commitText` again, which might replace that uncertain host range. The service now enters a fail-closed, visibly paused state after an uncertain host edit or selection/marked-range mismatch, invalidates candidates and performs no more text mutations until a fresh (non-restarting) input session. An input restart while a composition is active also pauses editing. On finish-input it does not call `finishComposingText` on a possibly changed connection; an active pending composition causes restarts to stay blocked. The user can switch keyboards while paused. A focus change or conservative callback may pause normal typing and a fresh input session relies on Android's session semantics; this is intentional until verified with real editors.

Pure Java guard regressions pass for uncertainty, restart and fresh-session transitions. The InputMethodService itself is **not compiled or tested**: the Android SDK and a real host are unavailable. Android may send selection callbacks in an order that causes premature pauses, and the behavior of old marked text on focus loss remains unverified. The guard cannot guarantee recovery of an edit already partially applied by the host. Do not use this experimental keyboard for valuable text until real-device tests establish safe behavior.

Candidate merging now rejects oversized candidates, malformed surrogate code units, control characters, Unicode line/paragraph separators and formatting controls (including bidirectional overrides), while allowing script joiners ZWJ/ZWNJ. This is a corruption guard, not a claim that the underlying dataset is accurate. Pure Java tests cover both rejection and valid joiners. Android UI/service compilation and device behavior remain unverified.

### Stale preview-action guard

“Use” and “Cancel choice” buttons capture the displayed Roman token, candidate value and generation. A queued event is ignored unless all three still match the active preview. This prevents a delayed button tap from committing or clearing a newer preview. The pure Java guard tests cover a changed choice, token and generation. The Android UI and `InputConnection` have not been compiled or exercised on a device; this test is not proof of host edit safety.

## Candidate-page experiment

When the configured per-page suggestion count is lower than the available candidates, Previous/Next controls expose subsequent pages while keeping the Roman original visible. Page controls and candidate buttons carry token, generation and page checks; changing page clears any hidden preview. Candidate buttons identify the selected preview in their accessibility description. Pure Java tests cover page boundaries, old-page actions, hidden candidates and stale tokens/generations. This service and its controls have not been compiled against the Android SDK or tested with Android, TalkBack, touch interaction or an actual editor; layout and text safety remain unverified. The paging path exposes at most the four currently retrieved suggestions, not a complete list of all dataset entries.

## Optional per-app language persistence

The setup screen includes an **off-by-default** switch to remember explicit Nepali/English changes by host package between launches. Enabling it does not save the current session automatically; only a later explicit language toggle in a non-literal field writes a choice. The app's private preferences hold at most 64 package identifiers and language values, never typed text, field contents or URLs. Literal-only and protected fields do not read or update saved choices. Turning the setting off removes the saved snapshot in the same preference transaction. The manifest disables Android backup. Invalid package identifiers and corrupt, duplicate, oversized or unknown-version snapshots are ignored; a new explicit choice can replace corrupt data. Failed writes are reported, with in-memory mode still available.

The opt-in state and snapshot use one local SharedPreferences file, with serialized in-process read/modify/write and a bounded versioned format. `tests/PersistenceTest.java` covers opt-in, opt-out, corruption, concurrent writers, eviction, failed writes and literal-field exclusions with an in-memory fake. Disk writes use `commit()` synchronously when the user changes a language, so device latency must be measured and a background transactional design considered if necessary. Android store/UI code remains uncompiled here because the Android SDK is unavailable. Actual cross-process behavior, package identity, protected-field callbacks, persistence across relaunch, storage failure handling, accessibility and UI still require Android tests. Host app names can be sensitive, so this feature is optional and off by default.

## Lookup backlog control

The experimental service uses a latest-only lookup scheduler: at most one lookup runs and one newer request waits; further requests replace that pending work. A focus/ownership change clears pending work, and the existing generation/token check still rejects a running lookup's stale result. Java concurrency tests cover 1,000 rapidly submitted requests, pending cancellation, exception recovery and shutdown. A running lookup can still finish after focus changes; it is not forcibly relied on for text edits. This reduces queue growth, but does not measure device latency or establish Android host/callback safety. The Android service remains uncompiled without its SDK, and a runtime lookup exception may leave suggestions empty until a later request.

### Queued touch safety

Ordinary keyboard buttons, including typing, Delete, mode and layout controls, capture a render generation. A subsequent render or `onFinishInput` invalidates prior buttons, so a queued old touch is ignored instead of acting on a newer editor or composition. Pure Java tests cover rerender and focus-loss invalidation. Because candidate results can cause a rerender, this conservative guard may also discard a legitimate touch queued during that refresh. The service assumes input lifecycle and button callbacks are serialized on Android's main thread; Android API compilation, actual focus ordering, touch responsiveness, accessibility and host behavior remain unverified without the SDK/device. This guard does not establish composition ownership or prevent same-document host edits.

## Experimental user-invoked recovery

When an in-session ownership check fails or a host edit has an uncertain result, the service pauses editing and retains at most the first 128-character printable Roman token **in memory for the current input session**. A visible, explicitly user-invoked “Copy retained Roman text” action can copy it to the system clipboard; nothing is copied automatically and no text is written into an uncertain host field. The control is suppressed in literal-only/protected fields, uses the existing rendered-action generation guard and is cleared on input start, finish, destruction or successful copy. On Android 13+ the clipboard item is marked sensitive; clipboard access and retention are governed by the OS and other permitted apps. The newest attempted key may be absent if the host did not confirm an edit, and the previous host's marked text may remain unresolved or be lost. Switching fields ends the recovery opportunity. The value is never displayed in the control itself.

Pure Java tests cover input bounds, protected-field suppression and clearing. The Android service and clipboard UI are uncompiled because the Android SDK is unavailable, so API compatibility, selection/focus lifecycle, clipboard privacy and actual host behavior remain unverified. This is not a data-loss guarantee; do not use the prototype for important or sensitive text.

## Lookup hardening and performance diagnostic

The index reader uses a bounded private 4 KiB window per lookup, rather than per-byte allocations and file reads. Candidate rows fail closed for overlong rows, too many candidates, empty entries, invalid UTF-8, non-Devanagari/non-joiner scalars and overly long values, matching the shared Swift row contract. The user still explicitly selects a suggestion; ranking and automatic conversion did not change. Java tests cover corruption and segment boundaries; 3,000 seeded actual-index keys produced identical candidate lists before and after. A single synthetic Mac/JDK hot-cache comparison is documented in `benchmark/README.md`; Android device performance remains unmeasured.


## Rejected phonetic fallback experiment

A Swift-phonetic-matching last-resort suggestion was evaluated and rejected because the frozen diagnostic showed excessive English candidate noise. It is not active in the service. See `experiments/phonetic-fallback/README.md` for the candidate snapshot, reproduction and limitations.

## Opt-in All Nepali suggestions

The experimental Android source adds an idle-row All control in ordinary Nepali text fields. It resets for each input session and retains the existing explicit-choice workflow: original Roman text is the default, and a suggestion requires preview and Use. When no indexed candidates exist, All can offer one `≈`-labeled approximate phonetic spelling for lowercase ASCII words of at least three letters. Indexed choices keep priority. This simple rule is not the Swift contextual engine and does not cover every spelling. The earlier synthetic probe found changed lists for 61 of 97 annotated English tokens when the same fallback was applied generally; the fallback is now limited to explicit All opt-in, but its quality remains unvalidated. Avoid using approximate choices without reviewing them. The Java core tests cover fallback boundaries and index priority. The Android service, UI, TalkBack and InputConnection behavior remain uncompiled and untested on a device because an Android SDK and Gradle are unavailable.
