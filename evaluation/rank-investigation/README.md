# Local candidate-ranking investigation

This is a 30-case, hand-labelled development diagnostic using synthetic two-word contexts; it is neither held out nor reviewed by a Nepali speaker. It does not measure population accuracy, native input method behavior, or privacy of the platform applications. No prior frozen probes were used. No project source files or typing defaults were changed.

`compare_dev.py` feeds the previous token into a new Swift `InputSession`, commits with context, then requests the target token. It compares against the same Android Java `SortedCandidateIndex` and `CandidateMerger` used by the service, with its authored, Aksharantar and Google sources and four-result cap. The separate Android original-text control is modeled, not exercised. Each input gets a fresh Swift session. The labels describe a plausible intended meaning, not universal word meanings.

On a fresh debug build, Swift's preferred text matched 29/30 labels; the labelled option was available in Swift 30/30 and in Android's suggestions or separate original control 29/30. The first non-original suggestions agreed on 17/30. Of 13 differences, Android had no candidate for 12, including 11 English cases with potentially misleading Swift phonetic guesses, plus `geet` where Swift supplied गीत. For `this is`, Swift's first non-original was इस while Android's was ईश. `yo pani` was expected पानी but both systems ordered पनि first; the spelling was available in both. On `the man` versus `mero man`, Swift picked English and Nepali respectively, while Android offered the same alternatives and preserved the literal default. The small sample and inconsistent treatment of context and candidate limits prevent a broad quality or platform-parity conclusion.

**Decision:** Keep Android's literal default. Do not copy the phonetic fallback wholesale or promote a dictionary candidate based solely on context. Shared ordering on curated entries is already largely aligned; the missing/wrong spelling cases need a broader speaker-reviewed development corpus and a separate untouched evaluation set. Any eventual context-sensitive implementation must reset at field/focus/language/literal boundaries, ensure stale asynchronous results cannot be applied, and not infer frequency from lexicographic source order. Context should be kept only in ephemeral memory and not sent to a server or retained in logs.

To repeat on the development Mac, build the current `portable-core` into `/tmp/lekha-rank-swift`, compile `SortedCandidateIndex.java`, `CandidateMerger.java`, and `evaluation/consistency-study/ServiceLookup.java` into `rank-investigation/classes` using an installed JDK, then run `python3 rank-investigation/compare_dev.py` from the task workspace. Results are local and contain only synthetic text. Native Android compilation and host UI were not tested; the helper does not exercise asynchronous focus or selection handling. Dataset licensing remains unresolved for distribution.
